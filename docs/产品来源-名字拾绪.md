Q:我想做一个浏览器书签扩展，我觉得现有的浏览器书签按照文件夹隔离的方式不能满足我，我目前想法是按照功能来区分，书签A比如属于多个领域，书签B也属于多个领域，比如AI、harness、博客文章，不同筛选方式可能出现相同书签，按照我要的归类，并且是动态过滤，你从第一性原理思考，有什么好的设计方式?
A:**我建议做成「一份书签 + 多维属性 + 动态视图」，而不是给文件夹增加多选功能。** 同一个网页只保存一份，你可以从“讲什么”“是什么”“用来干什么”等不同角度找到它。

更关键的是：**把“资料本身的属性”和“你查看资料的方式”分开。**

## 1. 从第一性原理看：收藏是为了未来找回，不是为了分类

收藏时，你知道网页讲什么；找回时，你可能只记得：

“那篇讲 harness 的文章”“之前存过一个能直接使用的工具”“准备做项目时参考的资料”。

所以，不应该要求你收藏时就决定它唯一的“住址”，而应该保存多个找回线索。这类通过多个属性逐步缩小范围的方式，在检索设计里叫**多面筛选（Faceted Search）**。([Algolia][1])

你举的例子里，有个值得拆开的地方：**AI、harness 是主题，博客文章是内容形态，并不是同一种分类。**

建议先提供四个维度，名称和选项允许自定义：

| 维度     | 回答的问题     | 一篇 harness 文章的属性示例 |
| -------- | -------------- | --------------------------- |
| 主题     | 它讲什么？     | AI、harness、上下文工程     |
| 形态     | 它是什么？     | 博客文章                    |
| 用途     | 我拿它干什么？ | 学习原理、项目参考          |
| 阅读状态 | 我处理到哪了？ | 待读                        |

主题、用途可以多选；阅读状态则是单选。**这些属性都不必在收藏时填完**，没有整理的内容也应该能保存和搜索。

相比把所有东西平铺成标签，这样至少不会把“AI、博客、重要、待读、工作”混成一锅。

## 2. 动态过滤：像逐步描述需求，而不是沿目录找东西

建议界面是：**左侧放常用视图，上方放搜索和已选条件，中间展示书签，旁边提供分维度筛选。**

例如，你逐步选择：

```text
主题：harness
形态：博客文章
用途：项目参考
```

得到的就是同时满足这三个维度的书签。筛选交互需要明确三个规则：

- **不同维度之间，默认“同时满足”。** 主题是 harness，并且形态是文章。
- **同一维度多选，默认“满足任意一个”。** 形态选文章和文档，意味着文章或文档；主题维度另外提供“全部满足”切换，用于寻找同时讨论两个主题的内容。这对应筛选中的 AND／OR 组合。([Algolia支持][2])
- **选项和数量跟着条件更新。** 比如选择 harness 后，展示相关的文章、仓库、文档各有多少，而不是始终展示全库的标签数量。动态属性值和计数也是多面筛选的重要部分。([Algolia][1])

一个容易做错的细节：**选中文章后，不要让同维度的“代码仓库”选项直接消失**，否则用户无法继续选择“文章或仓库”。我建议各维度的候选数量按*其他维度*的条件计算，已选条件始终可见、可撤销。

## 3. 最重要的设计：把常用筛选保存为“视图”

例如保存两个入口：

```text
「harness 待读」
主题包含 harness ＋ 形态是博客文章 ＋ 状态是待读

「项目参考资料」
用途包含项目参考
```

你的书签 A 可以同时出现在两个入口中，**不是复制了两份，只是被两组条件同时命中。**

以后收藏一篇符合条件的新文章，它自动出现在相应视图；读完后，它自动离开“harness 待读”，但仍留在“项目参考资料”。

因此，底层可以用这个心智模型：

```text
书签 = 网页 + 属性 + 收藏理由
视图 = 筛选条件 + 排序方式
```

**视图看起来可以像文件夹，但里面保存的是规则，不是书签。** 删除视图只删除这个入口，不应该删除里面的资料。

## 4. 比自动打标签更值得做的：记录“为什么收藏”

多标签本身已经有现成实现，例如 Raindrop 支持一个书签添加多个标签，并通过标签筛选。([Raindrop.io Help][3]) 因而，我不建议把“支持多个分类”当成产品的全部差异。

更值得围绕的区别是：

> **网页讲什么，和我为什么收藏它，是两件事。**

同一篇上下文工程文章，你可能是为了“学习原理”，也可能是为了“给自己的 harness 改造找实现参考”。

我建议在收藏弹窗里放一个**可跳过的一句话输入框**：

> 留着做什么？
> `以后优化游戏 agent 的上下文裁剪时参考`

这句话也参与搜索。它不是文章摘要，而是你的使用意图。

AI 后续可以建议主题和形态，但用途优先尊重你的记录；建议从已有分类中选择，不要每次自动创造一批新标签，更不要静默覆盖你的修改。

## 5. 第一版怎么收敛

**先把「收藏 → 多维筛选 → 保存动态视图」这个闭环做顺，不急着做知识图谱或 AI 聊天。**

实现上有一个关键边界：Chrome 原生书签 API 使用树形结构，书签节点有单一的父文件夹字段，公开属性中也没有标签字段。([Chrome for Developers][4]) 因此，我建议**扩展自己保存多维属性和视图，原生书签先作为导入来源**，不要靠在多个原生文件夹里复制书签来模拟多归属。

验证时，先导入你自己的几十条真实书签。隔几天分别尝试“按主题找”和“按用途找”，看看能否找到同一份资料，以及收藏时是否需要填写太多信息。

**这个产品的目标不是让你更勤快地整理，而是让你不必记住“当初放在哪”，仍然找得到。**

Q:同意书签＋上下文管理，我现在痛点就是，比如看到好几个世界模型的github项目和论文，没时间仔细研究，只想收藏，但是又不想直接放文件夹，导致tab一直开着，tab越来越多，不同topic都有这个问题。所以多维度书签＋记录摘要（当时的想法），我觉得很重要，因为思考碎片记录无法保存书签，做两个产品将来还能联动，也可能书签管理后面连接一个harness（本地服务或云服务），同时解决记录这一刻想法的需求
A:对，我觉得你现在已经把真正的问题说清楚了：

> **你不是缺一个“更好的书签管理器”，而是缺一个能把「当前网页 + 当下想法 + 未来用途」可靠卸载出工作记忆的系统。**

现在你一直开着 Tab，本质上是因为你**不信任收藏之后还能找回来、还能记得为什么收藏**。

所以产品第一目标应该不是整理，而是：

> **让我放心关掉 Tab。**

### 我会把一个收藏定义成 3 层

```text
Bookmark
├─ Source：它是什么
│  ├─ URL / Title
│  ├─ 页面摘要
│  ├─ 作者 / 来源
│  └─ 页面内容快照或索引
│
├─ Classification：它属于哪里
│  ├─ Topic: 世界模型 / Agent / Harness
│  ├─ Type: GitHub / Paper / Blog
│  ├─ Purpose: 待读 / 项目参考 / 学习
│  └─ Status: Inbox / Reading / Done
│
└─ Context：我为什么存
   ├─ 当时的想法
   ├─ 为什么值得看
   ├─ 我准备以后做什么
   └─ 收藏时间
```

其中我觉得**Context 是最重要、也是现有书签工具最容易缺失的一层**。

比如你保存一个世界模型项目：

```text
WorldDreamer GitHub

AI摘要：
基于视频预测构建交互式世界模型……

我的想法：
可能可以用于游戏 Agent 环境生成。
重点看看它如何定义 action → next state，
以后和我的游戏 benchmark 对比。
```

三个月后，AI 摘要告诉你：

> “这是什么？”

而你的那句话告诉你：

> **“我为什么当时觉得它值得留下？”**

后者价值往往更高。

## 不过我会稍微改变你说的“两个产品”

我不建议底层真的做成两个完全独立产品。

更合理的是：

> **两个入口，一个 Memory substrate。**

```text
              Personal Memory
             /               \
        Bookmark             Thought
       网页驱动              想法驱动
          │                    │
 URL + 内容 + 想法        纯文字 / 灵感 / 推理
          \                    /
             Shared Context
                   ↓
                Harness
```

用户看到的可以是两个产品：

**A. Bookmark 产品**

重点解决：

> `这个东西值得以后回来。`

浏览器里一键收藏。

**B. Thought 产品**

重点解决：

> `我现在脑子里出现了一个值得保留的想法。`

可能是快捷键、悬浮输入框、手机入口。

但底层对象应该能互相关联。

例如你后来写：

> “世界模型真正适合游戏的价值可能不是 NPC，而是 environment prediction。”

系统自动知道你之前有：

```text
Related:
• WorldDreamer GitHub
• Genie 论文
• GameNGen 论文
• 3个月前的一条世界模型想法
```

这时候它就开始从“书签”变成真正的**个人上下文系统**。

## 第一版我建议极度克制

你的 MVP 甚至只需要解决这个动作：

### `Ctrl/Cmd + Shift + S`

出现：

```text
────────────────────────────

World Models for Interactive Environments

摘要

为什么收藏？
┌─────────────────────────────┐

│ 以后用于游戏 Agent benchmark。  │
└─────────────────────────────┘

              保存并关闭 Tab
────────────────────────────
```

**“保存并关闭 Tab”甚至可以成为核心按钮。**

因为它直接针对你真实行为：

```text
看到有价值内容
↓
现在没时间
↓
怕以后找不到
↓
不敢关
↓
Tab 越来越多
```

你的产品应该变成：

```text
看到有价值内容
↓
一键 Capture
↓
AI 自动理解 + 我留一句话
↓
我相信未来找得回来
↓
安心关闭
```

---

还有一个我认为非常重要的产品判断：

**不要强迫收藏时整理。**

收藏时最好只要求用户做一件事：

> **可选地写一句“为什么留下”。**

Topic / Type / Summary 全让机器干。

甚至 Purpose 也可以先放 `Inbox`。

因为用户之所以让 Tab 堆积，本来就是因为**“现在没有精力处理它”**。如果你的收藏弹窗又让他填 4 个字段，你只是把“整理 Tab”的负担换成“整理 Bookmark”的负担。

所以第一性原理下，这个产品真正应该优化的指标不是“书签分类得多漂亮”，而是：

> **Capture friction 足够低，以至于用户愿意关掉 Tab；未来 retrieval 足够强，以至于用户敢关掉 Tab。**

这个指标我觉得比“多维书签”本身更接近你产品真正的核心。

Q:你先和我介绍Pinport、TagChoose、Bookmark Butler、FindMark的特点，我的差异点是什么，我是不是应该先做好基础功能自己体验一下？如果书签有主动功能，比如你打开ai文章，书签会主动提示，你的书签库里有以下类似书签，这个功能不知道有没有人喜欢.
A:**是，先把基础功能做到你自己愿意每天用。** 因为我查完之后发现：**“多标签 + 动态筛选 + AI 自动分类”本身已经不够成为差异点。你真正可能有价值的方向，是把书签从“存储工具”变成“浏览时主动调用的个人知识上下文”。**

### 这四个产品分别在做什么

| 产品                | 核心思路                                | AI                     | 和你最接近的地方       |
| ------------------- | --------------------------------------- | ---------------------- | ---------------------- |
| **Pinport**         | Tags 取代 Folder，多个 Tag 连续组合过滤 | 语义搜索               | **最接近你的动态过滤** |
| **TagChoose**       | AI 帮你判断应该存进哪些分类             | Gemini Nano 本地运行   | 自动分类               |
| **Bookmark Butler** | 强化版 Chrome Bookmark Manager          | AI Tag / Rename        | Saved Search + 多标签  |
| **FindMark**        | 搜索、AI整理、备份一体化                | AI推荐标题/文件夹/标签 | 多标签 + AI整理        |

### 1. Pinport：目前最值得你研究

Pinport 明确反对 folder，允许一个 bookmark 多个 tag，然后**连续选择 tag 缩小结果**：

```text
Harness
↓
Harness + Article
↓
Harness + Article + Learning
```

而且它的 tag 候选会动态变化，只显示继续选择后仍然有结果的 tag。这几乎就是你最开始说的“动态过滤”。([Pinport][1])

它现在还有**语义搜索**，可以直接搜“我之前看过的关于怎么集中注意力的文章”，不要求关键词完全相同。([Pinport][2])

甚至 Pinport 官方文档已经建议用户把 Tag 按不同语义使用：

> Project / Context、Topic、Priority、Content Type。([Pinport][3])

所以有一个重要结论：

**“Topic / Type / Purpose / Status 四维”这个想法很好，但本身不是足够强的产品壁垒。**

你的区别可以在于：Pinport 仍然是**扁平 Tag 系统**：

```text
#AI
#Harness
#Article
#Learning
#Unread
```

你的模型是有类型的：

```text
Topic   → AI / Harness
Type    → Article
Purpose → Learning
Status  → Unread
```

后者机器更容易理解，也更适合未来做自动化。

### 2. TagChoose：解决的是“收藏太麻烦”

它的思路非常明确：

> 我不想每次思考这个网页该放哪里，让 AI 帮我决定。

它使用 Chrome 的 Gemini Nano **本地分析**，自动推荐 Tag，然后把一个书签保存进多个对应 folder。数据不需要上传云端。([Chrome 网上应用店][4])

所以其实还是：

```text
AI
 ↓
帮你选择 Folder
 ↓
一个网页出现在多个 Folder
```

而你的方向应该是：

```text
AI
 ↓
理解网页属性
 ↓
形成结构化 metadata
 ↓
需要的时候动态生成视图
```

你不需要真的把书签复制到几个 Folder。

---

### 3. Bookmark Butler：Power User 工具

这个功能相当完整：

Chrome 原生书签双向同步、多 Tag、Domain 分组、Saved Search、模糊搜索、最近访问、重复链接、坏链接扫描、批量操作；AI 还能自动 Tag 和 Rename。([Chrome 网上应用店][5])

但它本质还是：

> **“把 Chrome 自带书签管理器变强。”**

而不是重新定义信息组织。

例如它最多给 bookmark 5 个普通 Tag：

```text
AI / Blog / Harness / Research
```

Saved Search 则保存：

```text
query + tag + domain
```

所以如果你只是做：

> 更漂亮的 SidePanel + Tag + Search

很容易变成 Bookmark Butler 的另一个版本。

---

### 4. FindMark：偏“书签管家”

FindMark 比较强调：

- fuzzy search
- 多标签
- AI 自动推荐 title / folder / tags
- Google Drive 备份
- 历史版本恢复
- 坏链接检测
- 回收站

([Chrome 网上应用店][6])

它解决的核心问题更像：

> **“我有几千个 Chrome 书签，怎么安全、高效地管理它们？”**

所以它做很多“运维”功能。

你不用和它卷这些。

# 那你的差异点到底是什么？

我现在会把之前的定位进一步改一下。

不是：

> **多维书签管理器**

而是：

> **会在你浏览互联网时调用你过去知识的个人上下文层。**

这是明显不同的产品方向。

你举的这个例子非常关键：

> 我正在看一篇 AI Harness 文章。

浏览器右边安静出现：

**你以前收藏过 3 个相关内容**

```text
DeepSeek Harness Architecture
相似度 91%
你收藏它是为了：研究 Plugin 生命周期

Anthropic Context Engineering
相似度 84%
你收藏它是为了：优化 Agent Context

你自己的备注
“Context 应该作为 harness 的核心状态”
```

这已经不再是：

> “我要去书签库找东西。”

而变成：

> **书签库主动参与我当前的信息消费。**

我认为这是你现在最值得深入的方向。

例如一个叫 **Sidebar Bookmarks** 的扩展明确提供：

- Rediscover 旧收藏

([Chrome 网上应用店][9])

所以：

**“人是否需要 Rediscovery？”——有明显产品信号。**

但我认为真正没解决好的，是：

> **什么时候主动出现，才有价值而不烦人？**

这才是你的产品问题。

# 我会怎么做第一版

我反而建议你**暂时不要上大量 AI 功能**。

先 dogfood 一个极小版本：

```text
① 导入 Chrome 书签

② 一个网页只有一份

③ Topic / Type / Purpose / Status

④ 多维动态筛选

⑤ 保存动态 View
```

你自己真实使用。

重点观察两个问题：

**问题 A**

> 我找东西的时候，四维系统真的比 Folder / Tag 更符合我的思维吗？

这是验证**组织模型**。

**问题 B**

> 我经常看网页的时候，会不会想：“我以前是不是收藏过类似东西？”

这是验证**主动上下文**。

如果 B 经常发生，那么第二阶段就非常明确：

```text
当前网页
     ↓
提取语义
     ↓
和 Bookmark Library 做 embedding 检索
     ↓
Top K Related
     ↓
达到阈值
     ↓
扩展 icon 出现一个小数字「3」
```

**不要直接弹窗。**

我特别建议这一点。

例如浏览器扩展图标：

> 🔖 **3**

你想看的时候点开：

> “发现 3 条与你当前页面高度相关的旧收藏。”

这样它是**主动发现，但不主动打断**。
