### B1: 同步推送 upsert 缺 userId 作用域，跨账号同 id 推送可夺取/覆盖他人书签行

**来源**: 代码路径审查 + 贝叶斯调查 + 黑盒复现（真实 HTTP）

**关联不变量**: INV-SPEC-01

**文件**: `apps/server/src/routes/sync.ts`

**位置**: 第 94-97 行（bookmarks）、第 108-111 行（views）

**严重程度**: P0

**置信度**: 已确认

**根因分类**: 实现过程偏移（隔离意图在预查与注释中明确存在，upsert 语句漏了作用域）

**问题描述**：
`bookmarks.id` 是全局主键（`db/schema.ts:24`）。push 预查带 `eq(bookmarks.userId, userId)` 判断 LWW，但随后的 `onConflictDoUpdate({ target: bookmarks.id, … })` 生成的 SQL 是 `ON CONFLICT (id) DO UPDATE SET …`——冲突行属于哪个用户完全不设防。账号 B 以已知 id 推送时：预查查不到（不属于 B）→ 跳过 LWW → 插入命中主键冲突 → **把 A 的行整体改写为 B 的内容并写上 user_id=B**。views 推送同构。

**不变量检查**：

- 规则：服务器按账号各存一份收藏，各账号数据互不混入（sync-archive spec feat01 前言）
- 来源：`docs/spec/sync-archive/spec.md:3`；`routes/snapshots.ts:17` 同仓自声明「userId 过滤一切查询」
- 触达路径：POST /sync（Bearer 认证通过）→ SyncPushRequestSchema.parse → LWW 预查（带 userId，形同虚设）→ onConflictDoUpdate（不带 userId）→ SQLite 落库
- 最小反例：GIVEN 账号 A 已推书签 id=X；WHEN 账号 B 持合法 token 以同 id=X 推送任意内容；THEN 返回 applied=1，A 的行被改写归属 B（已复现：A 视角 0 条，B 视角 1 条标题为 B 的内容）
- 结论：**破坏**

**贝叶斯更新**：

- H：upsert 冲突目标缺 userId 作用域
- 先验：中（`target: bookmarks.id` 与带 userId 的预查并存即自证）
- 支持证据：黑盒复现输出（临时 DB + 临时端口 + 两账号注册/推送/拉取全链路）；views 同构代码
- 削弱证据：id 为 uuid v4 随机，跨账号撞 id 需要知道目标 id；诚实客户端不会撞——但这不改变隔离判尺
- 反证检查：检查了 drizzle `onConflictDoUpdate` 语义（无 where 时更新一切冲突行）；检查了 `views` 同型；检查了 `taxonomies`（主键即 userId，无此问题）与 `snapshots`（查询全带 userId，无此问题）
- 更新后置信度：已确认

**Spec 对照**：

- 原始 spec / 契约：sync-archive spec「服务器按账号各存一份收藏」；snapshots 路由注释「userId 过滤一切查询」
- 当前实现 / 行为：`routes/sync.ts:94-97` upsert 不带 userId
- 分类：实现过程偏移

**影响**：
任一持合法账号的客户端可改写/夺走其他账号的书签或视图（需知悉目标 id）；同时意味着「同 id 数据在两账号间漂移」无需任何攻击意图的防护。反向影响：A 的书签凭空消失，与「各库互不混入」的产品承诺直接冲突。

**验证方式**：
复现脚本 `/tmp/x-threadpick-cr/repro-cross-user.ts`（临时 DB，未触碰仓库数据）：启动 server → 注册两账号 → A 推 id=X → B 推 id=X → 双方 pull 对比。修复后同脚本应输出「✅ 未复现」。

**修复建议**：
Drizzle `onConflictDoUpdate` 增加 `setWhere: and(eq(bookmarks.id, bookmark.id), eq(bookmarks.userId, userId))`（views 同理），使冲突行不属于当前用户时静默跳过（或按需返回 409）；同时补双账号隔离测试（B7）。

**处置结果**：✅已修复
**处置说明**：按方案实施——bookmarks/views 两处 `onConflictDoUpdate` 增加 `setWhere: eq(<table>.userId, userId)`（比原建议更简：预查已限定 id，setWhere 只需限 userId）；`applied` 计数改按 `.run().changes > 0` 自增，拒写行不再虚报。已在安装的 drizzle-orm 0.44.7 + better-sqlite3 内存库实测：跨用户同 id 推送 `changes=0` 行不动、本人 LWW 正常。

### B4: `since` 字典序比较依赖时间戳精度一致，秒精度输入会漏拉 1 秒窗口

**来源**: 代码路径审查

**关联不变量**: INV-CAND-02

**文件**: `apps/server/src/routes/sync.ts`、`apps/extension/src/db/sync.ts`

**位置**: `routes/sync.ts:44,52`（`gt(bookmarks.updatedAt, since)` 字符串比较）

**严重程度**: P2

**置信度**: 中

**根因分类**: spec 缺口

**问题描述**：
增量拉取用 ISO 串字典序比较。`SinceParamSchema`（`z.iso.datetime()`）接受秒精度 `2026-09-13T08:00:00Z`；它与库内毫秒形 `…T08:00:00.500Z` 逐字符比较时 `'Z' > '.'`，导致 08:00:00–08:00:01 之间的更新被排除在增量之外。当前唯一客户端恒发 `toISOString()`（恒毫秒+Z），不可达；但这是**隐式契约**——schema 不约束精度，任何第三方客户端或未来改动都可能踩中。extension 侧 `db/sync.ts:105` 的 `remote.updatedAt <= local.updatedAt` 同口径。

- 最小反例：GIVEN 服务器有行 updatedAt=`…T08:00:00.500Z`；WHEN since=`…T08:00:00Z`；THEN `gt` 为 false，该行漏拉
- 结论：未验证（当前客户端不可达，契约缺口成立）

**修复建议**：server 端把 since 转 `Date.getTime()` 与行的毫秒时间戳数值比较；或 schema refine 钉死 `\.\d{3}Z$` 精度并在 spec 回写。

### B5: normalizeUrl 用 localeCompare 排序参数，判重键跨环境不确定

**来源**: 代码路径审查

**关联不变量**: INV-CAND-03、INV-SPEC-03

**问题描述**：

**不变量检查**：

- 规则：URL 判重前规范化且结果确定
- 最小反例：`https://x.com/?b=2&a=1` 在两个 locale 下产出不同规范形
- 结论：破坏（潜伏）

**修复建议**：改序数比较 `a < b ? -1 : a > b ? 1 : 0`；加测试钉住参数排序确定性。
