# 同步推送跨账号隔离击穿（CR B1）修复报告

> 修复时间：2026-09-13 10:58
> 修复人：Claude (x-fix)
> 驱动：[reports/cr/cr-report-20260913-004910.md](../cr/cr-report-20260913-004910.md)（P0 B1 + 关联 B7）

## Bug 描述

CR 报告 B1（P0，黑盒确认）：`POST /sync` 推送的 upsert 以全局主键 `id` 为冲突目标且不带 userId 条件。账号 B 以账号 A 已有的书签 id 推送时，插入命中主键冲突后直接改写 A 的行并把 user_id 划归 B——跨账号数据夺取/覆盖。views 推送同构同病。黑盒复现：A 推书签 id=X 后 B 以同 id X 推送，A 视角该书签消失（0 条）、B 视角获得。

## 根因分析

`bookmarks.id` / `views.id` 是全局主键（非按账号命名空间）。LWW 预查（`select … where id AND userId`）带账号作用域，但随后的 `onConflictDoUpdate({ target: id })` 生成的 SQL 为 `ON CONFLICT (id) DO UPDATE SET …`，冲突行属于谁完全不设防——预查与写入动作的作用域不一致，写入侧漏了隔离条件。server 端无自动化测试、smoke 全部单账号链路（CR B7），该问题因此不可见。

## 修复方案

1. **隔离条件焊入写入动作**：bookmarks/views 两处 `onConflictDoUpdate` 增加 `setWhere: eq(<table>.userId, userId)`，生成 `ON CONFLICT (id) DO UPDATE SET … WHERE user_id = ?`——冲突行不属于当前用户时 UPDATE 静默跳过，行留在原账号名下。
2. **计数修正**：`applied` 计数改按 `.run().changes > 0` 自增（setWhere 拒写时 SQLite changes=0），不再把被拒行虚报为已应用。
3. **常驻回归反例（B7）**：`scripts/smoke.ts` 增加双账号隔离场景——注册账号 B，以账号 A 已推送的书签 id 推送（标题改为「B 冒名覆盖」），断言 B 的 `applied.bookmarks === 0`、A 再次 pull 该行标题/URL 原样、B 的库中不含该 id。

不采用的替代方案：composite unique index `(user_id, id)` 需放弃全局主键并做数据库迁移，而 id 为客户端 `crypto.randomUUID()`，诚实客户端永不碰撞，`setWhere` 已覆盖全部实际风险。
